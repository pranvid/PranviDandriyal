Talent Management Design System · SHL

Recruiters felt like they'd switched companies mid-task.

SHL's hiring workflow ran across five legacy products, each with its own front end. I owned the design system that replaced them: I measured the fragmentation, set the documentation standard, and ran the review of every component five squads built into it.

My role
Design system owner (design): audit, doc standard, component review
Team
~5 squads across Product, Design, Engineering, QA
Timeline
Core components ready for dev in 1 month
Stack
Figma library · Storybook · MUI + Carbon foundations

Four of the five legacy products. None of them agree on how a table, a button or a chart should look.

The problem

One hiring workflow crossed several products that looked and behaved nothing alike. In customer feedback, some users said it felt like landing on a different company's site, and every team rebuilt the same patterns from scratch.

What I did

Owned the system on the design side. Audited 117 UI patterns to size the gap, created the five-doc standard and templates every component follows, and assigned and ran design review for each component the squads built.

The outcome

A 55-component library, core pieces ready for dev in a month, adopted first by 7 squads and then company-wide. Delivery managers reported squads delivering about twice the work per sprint after adopting it.

01

The problem

Five products, five eras of front-end decisions, one recruiter stuck switching between them.

  1. Step 1

    TalentCentral

    Set up the hiring project and add candidates

    Continue
  2. Step 2

    iAssess

    Schedule and deliver the assessments

    Next
  3. Step 3

    Reporting

    Pull candidate scores and reports

    PROCEED
  4. Step 4

    Insights

    Compare people against the role

    Go →

One recruiter task, four products, four answers to “what does the next button look like”. Colours from the legacy products; buttons illustrative.

TC for projects and candidates, iAssess for assessment delivery, Reporting and Insights for analytics, Smart Interview for recorded interviews. A single hiring task could route a recruiter through two or three entirely different interfaces.

The move to a new Talent Intelligence (TI) platform was the chance to fix more than one experience: it could set how every future SHL product looks, feels and behaves.

  • Disconnected UI languages. The same action looked and worked differently in each product.
  • Inconsistent accessibility. Focus, contrast and keyboard behaviour varied product to product.
  • Repeated work. Every team rebuilt the same patterns from scratch.
  • Lost trust. In customer feedback, the interface changed so much between products that some users read it as a security concern.
  • No way to scale. Visual styles couldn't be maintained across product lines, let alone themed per client.

04

The strategy

SHL had tried a design system before. It hadn't landed, and there was no time to fail twice.

Updating the old products wouldn't fix consistency, performance or scale, so SHL was building a new Talent Intelligence platform from scratch, and it had to ship as soon as possible. The system underneath it had to be ready before the squads needed it, not months later.

Tried beforeMissed

A system built by an outside company

SHL had invested in a design system from an external agency.

What went wrong
It had a lot of misses. Built away from the product, it didn't fit how SHL's teams actually worked.
Ruled outToo slow

Build every component from zero

Design and engineer a bespoke library, pattern by pattern.

Why not
The TI platform couldn't wait months while we re-solved problems mature systems had already solved.
Chosen1 month

Adopt enterprise-grade foundations, build on top

Carbon for modular foundations, Material UI for flexible components, customised through SHL's own tokens.

Result
The core components were ready for dev within a month. The trade-off: living within two libraries' conventions, with our tokens on top so the brand never depends on either.

Principles written for HR software, not borrowed

“Be accessible” and “be consistent” are true of every system and settle no arguments. We wrote principles specific to what SHL sells and who uses it, so they could actually decide between two designs.

Principle 01

Accessible by necessity, not by audit

Candidates complete assessments under high-stakes, sometimes legally scrutinised conditions. WCAG 2.1 AA had to live in the tokens and components from day one, not in a later compliance pass.

Principle 02

Credible for high-stakes decisions

Recruiters make hiring calls on this surface. Every pattern had to read as authoritative and unambiguous: enterprise-grade, not consumer-cute.

Principle 03

White-label ready

Enterprise clients routinely ask for their own branding. Every token and component had to be re-themeable per client, colours, logos and type, without anyone touching the system underneath.

Principle 04

Scalable across a growing platform

Modular and reusable, built for mobile, tablet and desktop, and ready to expand as TI absorbs more of SHL's product line.

05

Tokens: where the principles become code

Principle 03 decided the architecture. If a client's brand had to change without anyone touching a screen, then no screen could reference a raw colour. So tokens run in layers, and each layer has one job.

Layer 1 · Base

What the value is

Raw values on a numbered scale, each shade tagged with its contrast ratio.

  • secondary-700
  • secondary-600
  • secondary-300
→
Layer 2 · Semantic

What the value is for

Named by purpose and state, never by colour. This is the only layer products consume.

  • background/button/primary/default
  • background/button/primary/hover
  • effects/focus-rings/focus-ring
→
Consumer

Where it lands

Every Figma component reads these names, and the specs hand the same names to engineering, so design and code share one vocabulary.

  • Button · Primary · Default
  • Button · Primary · Hover
  • Button · any · Focus

One value traced end to end: the primary button's teal is secondary-700, reached only through its semantic name.

08

Built squad by squad

We didn't build the library first and the platform second. We built both at once.

Around five squads were building SHL's new talent mobility platform. Whenever a squad picked up a screen, the components it needed were shared out across the squads, built, and put through the same checks before anyone else could use them. The library grew exactly as fast as the product needed it.

  1. 1

    A screen is picked up

    A squad starts a platform screen and lists the components it needs.

  2. 2

    Components are shared out

    Each missing component is assigned to a squad to design and build.

  3. 3

    Design review

    Design tests the build against the spec, and feedback goes back to whoever built it.

  4. 4

    QA and impact

    QA tests it, and the team checks how it's consumed in the application and what it affects.

  5. 5

    Published

    Handed off as the main version and marked ✅ ready for dev in the library.

10

Where it stands now: V2

We set up ownership for the design library. We never agreed a matching owner for the code.

Design defined the foundations in full: tokens, states, motion and theming, all documented in the Figma library. The coded library, Spectra, was built squad by squad, and without shared ownership across design and engineering those foundations were never implemented centrally in code. Missing pieces were patched locally, and around 30 tickets were raised for component gaps alone. Every squad paid the same component tax, and the cost stayed invisible because it was spread across everyone's sprint.

So we're pitching a full V2: a governed foundation, not another UI refresh, adopted incrementally rather than in a big-bang migration. In the meantime we fix components one at a time, as tickets inside current sprints.

  1. 01

    Figma and code drift

    Components aren't consistently built as designed.

  2. 02

    No foundation layer in code

    Tokens, states, motion and theming exist in Figma but aren't defined centrally in Spectra.

  3. 03

    Local overrides

    Teams edit components locally to unblock themselves.

  4. 04

    Repeated tickets

    The same component gaps become new dev work, again and again.

From the V2 proposal deck: why the current system isn't neutral. It keeps compounding inconsistency, accessibility gaps and delivery overhead.

A layered architecture, so change happens once at the right level instead of in every product.

11

Reflection

Measure before you argue

The audit turned “it feels inconsistent” into 21 of 117. That number did more for buy-in than any mock-up.

Adapt, don't reinvent

Carbon and MUI were the single biggest accelerant to quality and delivery speed.

Build as you go works, until it doesn't

Growing the library with the product kept it grounded in real screens. But five squads contributing means five interpretations, unless someone owns the whole.

What I'd do differently

Agree joint design and engineering ownership before the first component, not after the fiftieth. Status markers and review steps help, but only if someone on each side can say no.

Consistency is what builds trust: internally between teams, and externally for whoever uses what we ship. More than a component library, the system became the foundation the rest of SHL's Talent Intelligence platform builds on.
